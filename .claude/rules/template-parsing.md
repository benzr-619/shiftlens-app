# Template upload parsing conventions

Detail for `src/lib/parseUpload.ts` and `src/lib/template.ts`. Tolerant header-based
detection remains the core philosophy (decided 2026-07-12, unchanged): rename columns,
reorder them, vary casing — the parser still finds them. Don't quietly tighten this later
without checking back — it's a deliberate friendliness-vs-robustness trade for a
non-analyst ED manager handing the template to whoever pulls the export.

## History: where admit rate / boarding duration live has flipped twice

This matters for whoever touches this next, so the reasoning doesn't get re-litigated a
third time without context:

1. **2026-07-12 (original):** per-hour template columns, alongside Arrivals/ESI.
2. **2026-07-12 (walk-back):** moved to scalar typed number fields on a dedicated step.
   Reasoning: a manager testing the wizard had one overall admit rate for the period, not
   an hourly breakdown, and having both a scalar field *and* an hourly template column for
   the same input was confusing ("which box do I use?").
3. **2026-07-14 (reversed back to template, current state):** Ben (non-engineer, product
   owner) found it confusing that arrivals/ESI went through download-template/upload while
   boarding data went through typed number fields with checkboxes — a different
   interaction pattern for no good reason from a user's perspective. The fix this time
   isn't "put it back exactly as it was" — it's ONE consolidated multi-tab template
   covering everything, so there's exactly one way to get data into the app, period.

If a future session is tempted to move admit rate/boarding duration to typed fields again
("simpler for just one number"), re-read reason #3 first — the whole point this time was
interaction-pattern consistency, not a per-field ergonomics call. Don't flip it back
without checking with Ben.

## The consolidated template (`lib/template.ts`)

ONE downloadable `.xlsx` (`downloadConsolidatedTemplateXlsx`), four tabs, generated by
`generateConsolidatedTemplateXlsxBlob()`. No CSV variant for this template — multi-tab data
doesn't serialize meaningfully into one CSV, so CSV upload only supports the single-tab
Arrivals/ESI shape (see below).

- **Arrivals** — `Day`, `Hour`, `Average Arrivals`. 168 rows, required.
- **ESI Mix** — `Day`, `Hour`, `Average ESI 1-2 Count`, `Average ESI 3 Count`, `Average ESI
  4-5 Count`. 168 rows, optional, all-or-nothing (unchanged rule, see below).
- **Scalars** — `Field`, `Value`. Two rows: `Admit Rate`, `Mean Boarding Duration (hrs)`.
  Both optional, independently — providing only one does NOT make the other required; the
  admit-rate+boarding-duration *pairing* requirement (both-or-neither for boarding output
  to exist) is enforced downstream in `computeBoarding()`, not at the parse layer.

  **2026-07-22: Arrivals/ESI Mix columns relabeled "Average ___", and the Scalars
  `Boarding Duration (hours)` field relabeled `Mean Boarding Duration (hrs)`.** Reasoning:
  - Arrivals/ESI Mix were previously just "Arrivals"/"ESI N Count," ambiguous between "one
    arbitrary week's raw counts" and "the average for this hour-of-week across a full
    reporting period." The engine's math (`annualVisits = sum(arrivals) * 52` in
    `engine/allocate.ts`) only makes sense under the latter reading — each of the 168 cells
    is treated as a period average, not a single week's snapshot. The column header (and
    DataStep/data-team copy, `screens/setup/DataStep.tsx`) now say "Average" explicitly, and
    the copy states ESI Mix must be pulled over the *same* reporting period as Arrivals so
    the two stay consistent (a mismatched period would silently misweight the acuity curve).
  - `Boarding Duration (hours)` had the same ambiguity as the seasonality totals did before
    the mean-per-patient rework (see `.claude/rules/boarding-seasonality.md`) — unlabeled as
    mean vs. median vs. something else. Relabeled `Mean Boarding Duration (hrs)` and the
    copy now states explicitly it must be an average across all boarded patients in the
    period, not a median — same total-hours-conservation reason as the seasonality fields
    (duration multiplies directly into total boarding hours, so a ratio/consumer of this
    number needs a mean, not a median, to stay mathematically correct).
  - Admit Rate's field name is unchanged (still `Admit Rate` — there's no
    mean-vs-median ambiguity for a rate), but the DataStep/data-team copy now states it
    must be pulled over the same reporting period as Arrivals, to avoid a manager grabbing
    a single day's or week's admit rate against a full-year arrivals average.
  - Old headers (`Arrivals`, `ESI 1-2 Count`, `Boarding Duration (hours)`, etc.) are still
    recognized via `HEADER_ALIASES`/`SCALAR_FIELD_ALIASES` — this was a template-copy
    relabeling for clarity, not a tightening of what the tolerant parser accepts. Don't
    remove the old aliases; someone's saved/reused spreadsheet may still use them.
- **Boarding Seasonality** — ONE 4-column row set covering two independent small tables:
  `Month` / `Mean Boarding Duration by Month (hrs)` (12 rows, Jan-Dec) and `Day of Week` /
  `Mean Boarding Duration by Day of Week (hrs)` (7 rows, Sun-Sat, sharing the same 12-row
  block — day columns blank in rows 8-12). Deliberately laid out as one flat row-scan, not
  two stacked blocks, so it parses the same tolerant way as everything else (no positional/
  block parsing needed). **2026-07-22: these columns changed from raw TOTALS to MEAN
  boarding duration per patient** for that period — see `.claude/rules/
  boarding-seasonality.md` for the full reasoning (arrivals is one representative week
  reused for all 12 months, so a total conflated volume and duration seasonality; mean
  duration isolates the one effect the model can represent). Still not a per-day-of-week-
  per-month cross table — the engine derives a seasonality *index* from these means itself,
  the template never asks the user to pre-compute a multiplier.

Never seed any tab with example values (unchanged hard constraint) — every row ships blank
except the Day/Hour/Month/Day-of-week label columns themselves.

## Per-tab classification, not per-file

`parseXlsxFile` (`parseUpload.ts`) iterates **every sheet** in an uploaded workbook and
classifies each one independently by which columns it has — not by sheet name or position.
This means: a user can upload the full consolidated template, just a subset of tabs (e.g.
only Arrivals filled in), tabs renamed, tabs reordered, or even an extra stray tab (e.g.
instructions) — all tolerated. Three shape-detector functions
(`looksLikeArrivalsOrEsiSheet`, `looksLikeScalarsSheet`, `looksLikeSeasonalitySheet`) each
just check for the presence of that shape's key columns via `matchColumn()`. An
unrecognized sheet is silently skipped; only if NO sheet in the whole workbook is
recognized does `parseXlsxFile` return an error.

`matchColumn(headers, aliasTable)` was generalized (2026-07-14) to take the alias table as
a parameter instead of being hardcoded to one module-level table — this is what lets all
three sheet shapes reuse the same tolerant-matching algorithm without collision. Each shape
has its own alias table (`HEADER_ALIASES` for Arrivals/ESI, `SCALARS_HEADER_ALIASES`,
`SEASONALITY_HEADER_ALIASES`) — a header like "Day of Week" on the Boarding Seasonality tab
does NOT collide with the Arrivals tab's "Day" column, because they're matched by entirely
separate alias tables in separate parsing functions, never the same `matchColumn()` call.

Plain single-sheet CSV upload still works exactly as before (`parseCsvFile`, unchanged) —
it can only carry the Arrivals/ESI shape, since a CSV has no concept of multiple tabs.

## Header matching

`HEADER_ALIASES` normalizes headers (lowercase, strip non-alphanumerics) and matches
against a fixed alias list per field. Required columns (`day`, `hour`) must both resolve or
that tab errors with one message; partial required-column matches are not supported.
`arrivals` is matched the same way but is not required. `HEADER_ALIASES` only has entries
for `day`, `hour`, `arrivals`, `esi12`, `esi3`, `esi45` — admit rate, boarding duration, and
the seasonality means are matched by their own dedicated alias tables (below), not this one.
Each of `arrivals`/`esi12`/`esi3`/`esi45` carries both the bare form (`arrivals`,
`esi12count`, ...) and an `average`/`avg`-prefixed form (`averagearrivals`,
`averageesi12count`, ...) since the generated template's own headers now say "Average ___"
(2026-07-22) but older uploads/aliases without that prefix still need to resolve.

`SCALAR_FIELD_ALIASES` matches the **cell text** in the Scalars tab's `Field` column
(normalized the same way as headers) to a canonical key (`admitRate`/`boardingDuration`) —
this is a value-alias table, not a header-alias table; an unrecognized field-name row is
silently skipped (tolerant of extra rows, e.g. notes).

`MONTH_ALIASES` (built from `MONTH_NAMES` in `engine/types.ts`, full name + 3-letter
abbreviation, mirroring `DAY_ALIASES`) matches month-name cell values in the Boarding
Seasonality tab; numeric 1-12 (and 0-11) is also tolerated, same spirit as hour's 1-24
tolerance.

## Day/hour/month tolerance

- Day accepts full name or 3-letter abbreviation (case-insensitive), or numeric 0-6 / 1-7.
- Hour accepts 0-23 or 1-24 (24 maps to 23) — some hospital exports label hours 1-24.
- Month accepts full name or 3-letter abbreviation, or numeric 1-12 (also tolerates 0-11).
- All three live in `DAY_ALIASES`/`MONTH_ALIASES`/`parseHour()` — extend there, not inline
  in a row loop.

## All-or-nothing optional fields

ESI mix (168-row) and both boarding-seasonality totals (12-row / 7-row) are each accepted
only if **every row in that field's table** has a value — a partially-filled optional
field is treated as absent (with a warning), not partially applied. Same reasoning as
always: a sparse optional field is far more likely a data-entry mistake than an intentional
partial input, and silently half-applying it would violate the "never estimate from a
placeholder" rule (algorithm spec Section 1.2 / Section 8's admit-rate lesson). Do not
change this to a best-effort partial fill without re-reading that lesson.

Admit rate and boarding duration (the Scalars tab) don't need this rule — they're
independent single-value fields, no "partial" state possible for one number, and (per
above) they're allowed to be independently present/absent at the parse layer; the
both-or-neither pairing requirement lives in `computeBoarding()`, not here.

## NYPW / seeded-data constraint

The generated template (`template.ts`) must never contain example values in any tab —
every row ships blank except its label column(s) (Day/Hour, Field, Month/Day of Week).
This is a hard constraint from the original spec, not just a style choice: no ED-specific
data (validation or otherwise) may appear as a default anywhere in the shipped product.
